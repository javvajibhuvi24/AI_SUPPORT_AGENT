# Written Reflection — AI Customer Support Agent

## Design Decision

I chose to integrate the AgentCore Gateway tools by calling `await gateway_client.load_tools()` directly—without wrapping the call in a context manager block—before instantiating the Strands Agent. This meant all tools (Gateway MCP tools, Knowledge Base RAG, Code Interpreter, and Browser) are assembled into a single list and passed to the agent at construction time. This flat, declarative pattern keeps the `invoke` handler clean and straightforward: the agent receives a complete, fully-composed tool list each invocation, with no nested scoping that could lead to session-lifecycle bugs. The tradeoff is that a new MCP session and a fresh agent are created on every call, which introduces slight latency but greatly simplifies state management in a serverless runtime where connection reuse would be harder to guarantee.

## Challenge Encountered

The most significant challenge was the API mismatch between the Strands `MCPClient` and the version of the SDK installed in this environment. The starter code used `async with gateway_client:` followed by `await gateway_client.list_tools()`, but the installed SDK only supports a synchronous context manager (`__enter__`/`__exit__`) and exposes `load_tools()` (not `list_tools()`). Calling `load_tools()` inside the `with` block then caused a double-start error because `__enter__` already invoked `start()`. Resolving this required removing the context manager entirely and calling `await gateway_client.load_tools()` directly, which allows the client to lazily start its own session on first use. Similarly, the `code_session` context manager yields a session object but the inner method is `execute_code()`, not `invoke("executeCode", ...)`. Discovering and fixing these SDK-level differences required tracing tracebacks, inspecting source, and iterating—a common reality when working with rapidly evolving cloud-native SDKs.

## Production Consideration

In a real customer-facing deployment, the Gateway's authorizer must be secured before go-live. This project uses the `NONE` authorizer on the AgentCore Gateway for simplicity, which means any HTTP client that knows the endpoint URL can call the order-tracker and refund-processor Lambda functions without authentication. In production, the Gateway should use AWS SigV4 or a JWT-based OAuth flow to verify that requests originate from the trusted AgentCore runtime and are associated with the authenticated customer session. Additionally, the `customer_id` used as the `actor_id` for memory namespacing should be a verified, backend-issued identifier—not a client-supplied string—to prevent one customer from accidentally retrieving another's memory records. These two controls together (Gateway auth + verified actor IDs) are the minimum baseline required before handling real customer PII.
